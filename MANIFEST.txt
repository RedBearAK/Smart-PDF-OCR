FIELD REPORT THIS ANSWERS (M1 mini, 16GB, 82-page 400dpi batch)

  gap between "error patterns: N loaded" and the workers line.

WHAT CHANGES

  1. macOS memory probe rebuilt. The old vm_stat formula (free + inactive +
     speculative) undercounts badly: unified-memory machines keep their real
     headroom in caches, and inactive anonymous pages may be dirty and
     swap-bound anyway. New order:
       primary   memory_pressure's "System-wide memory free percentage"
                 x hw.memsize -- Apple's own pressure-based availability
       fallback  vm_stat free + purgeable + file-backed (the pool behind
                 Activity Monitor's "available": free + cached files)
     Linux /proc/meminfo path unchanged. On the reported machine this should
     read ~10GB -> memory allows 8 -> core bound wins -> 4 workers.
     field_rgx: MEMORY_PRESSURE_PCT_rgx, VM_STAT_PURGEABLE_rgx,
     VM_STAT_FILE_BACKED_rgx added; the inactive/speculative regexes removed.

  2. The silent gap was rasterization: the parent renders all pages before
     sizing runs, and at 400dpi x 82 pages that is many mute seconds.
     enumerate_pages/_rasterize_pdf/_rasterize_with_pdfium now thread an
     optional (done, total) progress callback, and the CLI shows
     "  rasterizing page X/Y" in the same style as recognition (the
     _progress helper gained a verb parameter). Bundles, bare images, and
     the poppler subprocess path do not narrate; only the pdfium loop does.
     No behavioral change for callers that pass nothing.

  Expected stderr sequence after this:
      error patterns: 21 loaded
        rasterizing page 82/82
      workers: 4 (8 cores -> 4, 10.2GB free -> 8 @ 900MB/worker, 82 pages)
      loading recognizer in 4 workers (onnxruntime + models)...
        recognizing page 82/82

  On the 50% btop saturation: that is the sequential engine's own intra-op
  threading, and it is the expected ceiling at 1 worker. It should climb
  substantially at 4 workers x 2 capped threads.
