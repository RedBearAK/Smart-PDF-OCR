WHAT CHANGES

  1. Parallel recognition, sized to the machine. A new --workers flag:
     'auto' (the default) sizes a spawned process pool from three bounds and
     announces the arithmetic on stderr --

         workers: 4 (8 cores -> 4, 9.6GB free -> 10 @ 700MB/worker, 82 pages)

     Core bound: cores // 2, each worker's engine capped at 2 intra-op
     onnxruntime threads (the engine's own threading already spreads one page
     across cores; workers multiply that). Memory bound: reclaimable RAM
     (Linux /proc/meminfo MemAvailable; macOS vm_stat free + inactive +
     speculative pages -- the pool unified memory reclaims gracefully) minus a
     headroom floor of max(2GB, 25%), divided by the measured worker cost
     (700MB at <=300 dpi, 900MB above). Page bound: never more workers than
     pages. Hard cap 8, floor 1. A failed memory probe retreats to 2 workers
     and says so. --workers N pins the count (bounded by pages);
     --workers 1 takes the original sequential path untouched.

  2. Fail-loud pool semantics. Workers are spawn-context processes (fork is
     unsafe under onnxruntime), each with its own engine, warmed in the pool
     initializer. A page that fails aborts the whole run naming that page.
     Results reassemble in page order before correction runs, so nothing
     downstream of recognition changes at all. Ctrl-C terminates the pool via
     the context manager and exits 130 as before.

  3. Startup announcement. Both paths now print a line before the multi-second
     import + model load ("loading recognizer (onnxruntime + models)...";
     the pool flavor names the worker count), so the warm-up gap no longer
     looks like a hang. Suppressed by --quiet, like the progress line.

  4. rapidocr_backend gains set_engine_params() (construction params, refused
     after the engine exists) and warm_engine(). field_rgx gains the five
     memory-probe regexes (MEMINFO_AVAILABLE_rgx, VM_STAT_*_rgx).

  No changes to: container.py (the parent still rasterizes; workers receive
  image paths and return PageResults), the correction layer, outputs, or any
  interface other than the new flag. --cached runs never size a pool.

TESTS

  tests/test_parallel.py: 12 tests -- canned meminfo/vm_stat parsing, every
  sizing bound (core, memory, dpi cost, page count, cap, floor, failed probe,
  pinned), a live memory probe, and two real spawned-pool tests: 2-worker
  output must exactly match the sequential path in text and page order with
  monotonic progress ticks, and a missing page image must abort naming the
  page. The pool tests skip when rapidocr or Pillow is absent.

  Full suite after application: 119 passed, pyflakes clean. End-to-end
  verified on a 4-page PDF: pooled and sequential corrected output identical,
  --pdf-out unaffected.

EXPECTED RESULT ON THE 16GB MACHINES

  Auto-sizing resolves to 4 workers (core-bound) on both. The 82-page batch
  should land around 2 to 2.5 minutes against the 5-minute sequential run --
  measure once to confirm; if the gain disappoints, the engine's pre-existing
  intra-op parallelism is the suspect, and pinning --workers against a
  stopwatch will show the true curve. Rasterization stays serial in the
  parent (measured at 0.1-0.5 s/page, not worth worker-side rendering yet).
